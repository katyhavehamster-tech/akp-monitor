# Архітектура АКП-Монітор

## 1. Компоненти

| Рівень | Технологія | Призначення |
|---|---|---|
| Інтерфейс | React 19, TypeScript, Vite, Recharts | Кабінети уповноваженого, керівника, виконавця, технічного адміністратора та внутрішнього аудитора |
| Прикладний рівень | Django 5, Django REST Framework | REST API, рольова модель доступу, бізнес-логіка |
| Безпарольна безпека | `key_crypto.py`, Web Crypto API | Ключі AKP-KEY-V1 (ECDSA P-256, AES-256-GCM, PBKDF2), Challenge-Response |
| Сесії та захист | модель `UserSession`, `/admin/keys` | Живий моніторинг активних сесій, миттєве примусове завершення, Anti-Lockout |
| Верифікація звітів | модель `ReportSnapshot`, `/verify` | Підпис HMAC-SHA256 (перевірка у сталий час), QR-коди за ДСТУ 4163:2020 |
| Правила | `rules.yaml` | Явні правила сигналів Risk Flags, ризику невиконання і рекомендацій; змінюються без програміста |
| Аналітичне ядро | `rules.py` | Детерміновані розрахунки без ШІ: сигнали, моніторинг, звіт для Порталу, рекомендації, довідка |
| Документи | `docgen.py`, `reports_docx.py` | Формування документів Word за ДСТУ 4163:2020 |
| Опитування | `surveys.py` | Імпорт і порівняння результатів Google Форм без електронних адрес |
| Самоперевірка | `selfcheck.py` | Звірка з ключем сигналів і еталонним звітом організаторів |
| Журнал дій | модель `AuditLog` | Записи з ланцюжком хешів SHA-256 (розширений режим аудиту ІзОД) |
| Підтвердні матеріали | модель `Evidence` | Незмінні файли з контрольною сумою SHA-256 |
| Інтеграція | `/api/docs` | Специфікація OpenAPI (Swagger), локалізована в Air-Gapped контурі |
| Зберігання | PostgreSQL 16 (Docker) або SQLite (локально) | Дані системи; файли підтверджень — у томі `media` |

## 2. Модель даних

Основні сутності: орган, програма, розділ програми (R1–R3), захід, корупційний ризик, вимірювання індикатора ризику,
інформація про виконання за квартал, підтвердний матеріал, коментар, рішення про перенесення строку, звітний період,
рекомендація, запис журналу дій, опитування, профіль користувача (роль, підрозділ, посада).

Ключові рішення:

1. Квартальний звіт кумулятивний: стан на кінець ІІ кварталу дорівнює стану на кінець півріччя. Тому звіт для
   Порталу за І півріччя формується з періоду 2026-Q2, за ІІ півріччя — з періоду 2026-Q4.
2. Індикатор виконання і індикатор ризику — різні показники. Перший показує, що захід зроблено; другий — що ризик
   зменшується. Сигнал «формальне закриття» (RF3) виникає саме з розриву між ними.
3. Строк у затвердженій програмі не змінюється: перенесення фіксується як окреме внутрішнє рішення з причиною й автором.

## 3. Потік даних: «внесли один раз — використали багато разів»

1. Виконавець за один крок вносить статус, фактичну дату, значення індикатора, опис і підтвердні матеріали.
2. Система одразу виконує попередню перевірку за правилами і показує сигнали ще до погодження.
3. Координатор погоджує інформацію або повертає її із зауваженням.
4. З тих самих даних автоматично формуються: моніторинг і панелі, стан корупційних ризиків, сигнали Risk Flags,
   рекомендації, внутрішній звіт (XLSX, CSV), аналітична довідка (Word) і звіт для Порталу НАЗК (XLSX, CSV, Word).
5. Кожна дія фіксується в журналі дій.

## 4. Безпека і розгортання

1. Один Docker-образ (gunicorn і whitenoise) та PostgreSQL. Зовнішні хмарні сервіси і CDN не використовуються, тому
   систему можна розгорнути в закритому відомчому контурі (Air-Gapped Ready).
2. Безпарольна автентифікація за файлом електронного ключа `.key` (ECDSA P-256, AES-256-GCM, PBKDF2 100 000 ітерацій)
   зі строком дії (90, 180 або 365 днів), можливістю дострокового відкликання та захистом Anti-Lockout для адміністратора.
3. Живий моніторинг активних сесій користувачів (`UserSession`) і можливість їх примусового миттєвого завершення адміністратором.
4. Персональні дані не обробляються: користувач описаний кодом, роллю, підрозділом і посадою.
5. Підтвердні матеріали не можна змінити чи видалити; цілісність файлів перевіряється за SHA-256.
6. Журнал дій незмінний; перевірка ланцюжка хешів SHA-256 показує номер першого зміненого запису. У режимі ІзОД
   до журналу протоколюються не лише зміни, а й кожен перегляд картки, завантаження доказу та друк документа.
7. Криптографічний підпис зліпків звітів `HMAC-SHA256` (перевірка у сталий час) та публічна перевірка справжності
   документів за QR-кодом на `/verify`.

## 5. Масштабування на інші органи

Орган і програма — окремі сутності; підрозділи, ризики й заходи привʼязані до програми. Для нового органу достатньо
імпортувати його програму і реєстр ризиків у тому самому форматі CSV, що й набір організаторів. Правила
в `rules.yaml` спільні, але пороги можна налаштувати для конкретного органу.
