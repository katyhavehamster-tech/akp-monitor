# Аналіз можливих зловживань і запобіжників

| Можливе зловживання | Як проявляється | Запобіжник у системі |
|---|---|---|
| **Формальне виконання** | захід «виконано», ризик не змінився | оцінюється індикатор стану ризику, а не кількість закритих заходів; сигнал RF3; рекомендація переглянути ефективність заходів |
| **Порожній або скопійований опис** | опис переказує зміст заходу | RF4 (подібність ≥ 0,6 і немає цифр/посилань), RF7c для невиконаних без пояснення; попередня перевірка до подання |
| **«Виконано» без доказів** | немає документів | RF2; підказка потрібних підтверджень; рядок помічається в службовому полі звіту |
| **Підтвердження «заднім числом»** | документ датований пізніше виконання | RF7b; дата і час завантаження фіксуються в журналі |
| **Підміна документа після погодження** | файл замінено | матеріали незмінні (лише нові версії), SHA-256 кожного файлу, перевірка цілісності |
| **Тихе редагування історії** | змінено статус або видалено запис | журнал дій із ланцюжком хешів; перевірка показує номер першого зміненого запису |
| **Нескінченні перенесення строків** | строк переносять, щоб не бути простроченим | RF1 рахується від строку **програми**, а не внутрішнього; RF6 при ≥ 2 перенесеннях; кожне перенесення має причину і автора |
| **Вибіркова звітність підрозділу** | підрозділ не вносить проблемні заходи | система показує, хто не вніс інформацію; ризик невиконання росте за відсутності внесення |
| **Тиск через рейтинги** | підрозділи «підганяють» показники | карта підрозділів **без рейтингування**, упорядкована за кодом |
| **Використання системи для покарання людей** | висновки про конкретну особу | користувачі без ПІБ; оцінюються заходи і ризики, а не особи; рекомендації адресуються підрозділу |
| **Автоматичні рішення без людини** | система «сама» змінює статус чи карає | ШІ не використовується для висновків; правила відкриті (`rules.yaml`); рекомендація лише пропонується, рішення ухвалює посадова особа з відповідальним і строком |
| **Маніпуляція правилами** | хтось тихо змінює пороги | правила лежать у репозиторії, зміни видно в історії git; пороги показуються в інтерфейсі |
| **Надмірний доступ** | виконавець бачить чужі заходи | рольова модель на рівні API: виконавець отримує лише свій підрозділ; керівник лише переглядає; техадмін не змінює зміст |
| **Деанонімізація в опитуваннях** | відповіді малої групи вказують на людину | e-mail і позначки часу не зберігаються; результати груп, менших за мінімум (5), не показуються |
| **Зловживання вікном внесення** | правки після погодження | поза вікном виконавець не може змінювати дані; погоджене виконавець не змінює; позачергове відкриття вікна фіксується в журналі |

## Залишкові ризики

- Достовірність даних самозвітування: система ловить ознаки, але не замінює перевірку. Тому план —
  наповнювати індикатори ризиків з первинних систем (див. integration.md).
- Пороги правил (10 % шляху, 0,6 подібності) взяті з набору організаторів і потребують калібрування на реальних даних.
